# PRD 작성용 메타 프롬프트 — 노션 연동 견적서 웹뷰 & PDF 다운로드 MVP

이 문서는 실제 PRD가 아니라, **PRD를 작성시키기 위한 메타 프롬프트**다. 아래 프롬프트 원문을 그대로 Claude Code(또는 다른 LLM)에게 입력해 PRD 문서를 생성한다.

## 사용 방법

1. 아래 "메타 프롬프트 원문" 섹션 전체를 복사한다.
2. 새 대화 세션에서 그대로 붙여넣는다. 필요시 `[ ]`로 표시된 placeholder를 채운다.
3. 산출물은 `docs/PRD.md`로 저장하도록 지시되어 있다.

---

## 메타 프롬프트 원문

```
당신은 시니어 프로덕트 매니저입니다. 아래 조건에 맞는 MVP PRD(제품 요구사항 문서)를
작성해서 docs/PRD.md 파일로 저장해 주세요.

# 배경
- 서비스명: [서비스명을 입력하세요, 예: Invoice Web]
- 한 줄 설명: 노션(Notion)에 입력한 견적서 데이터를 클라이언트가 별도 로그인 없이
  웹 링크로 확인하고, 필요시 PDF로 다운로드할 수 있는 서비스
- 사용자 유형
  1) 발행자(내부 사용자): 노션 데이터베이스에 견적서 항목을 입력/관리한다.
  2) 클라이언트(외부 사용자): 발행자가 공유한 링크로 접속해 견적서를 웹에서
     확인하고, PDF로 다운로드한다.
- 기술 스택 제약: Next.js(App Router) / React / TypeScript / Tailwind CSS 기반
  웹 애플리케이션. Notion을 CMS 겸 데이터 입력 도구로 사용하며, Notion API로
  견적서 데이터를 읽어온다. (구체적인 프레임워크 버전, UI 라이브러리, 배포 환경은
  현재 리포지토리의 CLAUDE.md를 참고해 결정하세요.)

# 요청 사항
아래 목차 순서로, 각 항목을 빠짐없이 작성하세요. 항목마다 근거나 트레이드오프를
간단히 덧붙이고, 확정할 수 없는 부분은 "결정 필요" 항목으로 명시하세요.

1. **문제 정의 및 목표**
   - 현재 견적서 공유 프로세스의 문제점 가정
   - 이 MVP로 해결하려는 핵심 문제 1~2가지
   - 성공 지표(예: 링크 조회율, PDF 다운로드율, 발행자 작성 소요 시간 등)

2. **범위 정의 (In Scope / Out of Scope)**
   - MVP에 반드시 포함할 기능
   - 명시적으로 이번 범위에서 제외할 기능(예: 결제 연동, 다국어, 견적 승인/전자서명,
     알림톡/이메일 자동 발송 등) — 제외 이유 포함

3. **사용자 시나리오 (User Flow)**
   - 발행자: 노션에 견적서 항목 입력 → 웹 링크 생성/공유까지의 흐름
   - 클라이언트: 링크 접속 → 웹에서 견적서 확인 → PDF 다운로드까지의 흐름
   - 각 흐름을 단계별 리스트 또는 mermaid 시퀀스 다이어그램으로 표현

4. **핵심 기능 명세**
   - 노션 데이터 연동: 어떤 프로퍼티(항목명, 수량, 단가, 합계, 공급자 정보,
     유효기간 등)를 읽어올지, Notion 데이터베이스 스키마 가정
   - 견적서 웹뷰: 라우팅 방식(예: `/quote/[id]`), 필요한 정보 표시 항목,
     반응형 대응 여부
   - PDF 다운로드: 생성 방식 후보 비교(예: 브라우저 인쇄 API, 서버사이드
     HTML-to-PDF 라이브러리, 외부 API 등)와 MVP에서 선택할 방식 및 근거
   - 접근 제어: 로그인 없는 공개 링크 vs 만료/토큰 기반 접근 제한 등 보안 수준 결정

5. **데이터 모델 및 연동 구조**
   - Notion 데이터베이스 ↔ 웹 애플리케이션 간 데이터 흐름 다이어그램
   - 캐싱/재검증 전략(Notion API 호출 빈도, ISR/on-demand revalidation 여부)
   - 에러 상황 처리(노션 항목 삭제/비공개 전환, API 실패 등)

6. **비기능 요구사항**
   - 성능(초기 로딩, PDF 생성 시간 목표치)
   - 보안(공개 링크 추측 방지, 민감정보 노출 범위)
   - 접근성 및 다국어 여부(MVP 범위 내 결정)

7. **화면 정의 (Screens)**
   - 필요한 페이지 목록과 각 페이지의 핵심 컴포넌트
   - 페이지별 상태(로딩/에러/빈 데이터) 처리 방침

8. **마일스톤 및 일정 제안**
   - MVP를 2~3단계로 쪼갠 릴리즈 계획(예: 웹뷰 우선 → PDF 다운로드 → 접근 제어 강화)
   - 각 단계별 완료 기준(Definition of Done)

9. **리스크 및 오픈 이슈**
   - 기술적 리스크(Notion API rate limit, PDF 렌더링 품질 등)
   - 의사결정이 필요한 항목 목록

# 출력 형식 및 제약
- 전체 문서는 한국어로 작성하세요.
- Markdown 문서로 작성하고, 표/리스트/mermaid 다이어그램을 적극 활용해 가독성을
  높이세요.
- 각 섹션 제목은 위 목차의 번호와 제목을 그대로 사용하세요.
- 기술 스택이나 라이브러리를 특정할 때는 반드시 현재 리포지토리의 CLAUDE.md에
  명시된 제약(예: shadcn/ui base-nova 스타일, Tailwind CSS v4, Next.js 16의
  PageProps/LayoutProps 규칙 등)과 충돌하지 않는지 확인하고 작성하세요.
- 불확실하거나 사용자 확인이 필요한 사항은 추측으로 채우지 말고 "결정 필요"로
  명시하세요.
- 완성된 문서를 docs/PRD.md 경로에 저장하세요.
```

## 메타 프롬프트 설계 노트

- **역할 부여**: "시니어 프로덕트 매니저"로 역할을 고정해 기능 나열이 아니라 문제
  정의 → 범위 → 시나리오 → 명세 순의 PRD 구조를 유도한다.
- **범위 제한(Out of Scope) 강제**: MVP가 산으로 가지 않도록 제외 기능을 명시적으로
  쓰게 했다.
- **기술 스택 제약 주입**: 이 리포지토리는 `base-nova`(Radix 아님) 기반 shadcn/ui,
  Tailwind v4, Next.js 16의 `PageProps`/`LayoutProps` 등 일반적인 Next.js 예제와
  다른 컨벤션을 쓰므로, PRD 작성 시점부터 CLAUDE.md 참조를 강제해 실제 구현 단계에서
  충돌하는 걸 방지한다.
- **PDF 생성 방식 비교 요구**: 브라우저 인쇄 vs 서버사이드 렌더링 vs 외부 API 등
  구현 난이도가 크게 갈리는 결정 지점이라 PRD 단계에서 후보 비교를 명시적으로
  요구했다.
- **"결정 필요" 항목화**: LLM이 불확실한 정보를 그럴듯하게 지어내지 않도록,
  확정 불가능한 사항은 오픈 이슈로 분리하게 했다.
